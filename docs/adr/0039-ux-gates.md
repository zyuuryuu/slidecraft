# ADR-0039: UX ゲート — 原則は規格・研究から引き、予算は ratchet で守る（ADR-0031 の G4）

- Status: Accepted（2026-11-08・方向性はユーザ合意。数値は現在値で固定し、運用で更新）
- Date: 2026-11-08

## Context

2026-11-08 の Windows 実機確認でユーザから「ボタンが多くて気になり始めた」と指摘があり、棚卸しで 4 件の Issue
（#612 テンプレ操作の集約・#613 帯を 1 本に・#614 上部バーを文書操作だけに・#615 細部）になった。どれも個々には
正しい機能追加の結果で、悪くしたのは**足し算の総和**だった。

コードの劣化には [ADR-0031](0031-maintainability-gates.md)（G1 構造規約テスト・G2 一致テスト・G3 傾向センサス）が
あり「レビューで気づく」から「CI で赤くなる」に移っている。UX の劣化だけが、ユーザが実機で気づくまで誰も止められない
構造に残っていた。

ユーザの要求は「実測の数値だけでなく、UX の基本原則＝世の中の研究を参考に、よりよい定義を置く」こと。2026-11-08 に
一次資料を確認した結果（[docs/design/ux-principles.md](../design/ux-principles.md) §8）、次が使える:
ISO 9241-11（効果・効率・満足）、ISO 9241-110:2020 の 7 原則、ISO 9241-210 の人間中心設計、Nielsen の 10 ヒューリスティクスと
重大度 0〜4、Shneiderman の 8 黄金律、Norman の基本原則、Hick／Fitts／Miller–Cowan／Tesler／段階的開示／ゲシュタルト／
Doherty／認知負荷理論、SUS／UMUX-Lite、KLM、HEART、WCAG 2.2、Apple／Microsoft の HIG。

## Decision

ADR-0031 の 3 層に **G4: UX ゲート**を足す。詳細と根拠は [docs/design/ux-principles.md](../design/ux-principles.md)。

### G4-a. 定義と原則の権威（文書）

- 「UX が良い」の定義は **ISO 9241-11（JIS Z 8521）の効果・効率・満足**とする。評価対象の場面は「原稿を持った業務
  ユーザが 1 人で、デスクトップで、AI の助けを借りてスライドを作る」に固定する。
- 設計原則は **ISO 9241-110:2020 の 7 原則を骨格**に、Nielsen／Shneiderman／Norman を対応づけた 1 枚の表
  （ux-principles.md §2）を正本とする。独自の原則は作らない。本プロジェクトでの読み替え 7 規則（1 画面 1 目的・入口は
  1 か所・記号は 1 対 1・語は辞書経由・文書操作と設定を混ぜない・複雑さは AI と既定値が負う・取り消せる）は、その原則から
  導いた**運用規則**であり、原則そのものではない。

### G4-b. UX 予算（CI 必須・fail する・ratchet）

- 定量化できる法則（Hick・Fitts・Miller–Cowan・段階的開示・認知負荷・WCAG 2.2 AA）から**予算項目**を導き、
  `tests/ux-budget.test.tsx` に集約して現在値を上限として固定する。初期値は現在の実装の値（常設ボタン ≤ 7・帯 1 本・
  メニュー区画 ≤ 4・記号 1 対 1 の許可リスト・i18n 漏れ 0・標的 ≥ 24×24 CSS px・ネスト ≤ 2・代表タスク 3 本の KLM 予測時間）。
- **数値は ADR に書かない。テストが正本。** 上げる変更は PR 本文に理由（どの原則をどう満たすか・複雑さを誰が負うか）を
  書き、レビュー統括が承認する。下げる変更（ボタンが減る等）は UX 改善の実測値として shipped.md に 1 行。

### G4-c. レビューはヒューリスティック評価（プロセス）

- GUI を触る PR は、レビュー Agent（または人）が Nielsen のヒューリスティック評価の形式で報告する: 原則 → 違反箇所 →
  重大度 0〜4。**重大度 3 以上はマージ阻害**、2 以下は Issue 化。
- PR テンプレートに「UX への影響」欄を足す（常設の追加・入口の移動／追加・記号と文言・複雑さを誰が負うか）。
  GUI を触らない PR は「該当なし」1 行。

### G4-d. ユーザ評価は UMUX-Lite と実機確認（節目ごと）

- 節目（リリース前・大きな UI 変更後）に **UMUX-Lite 2 問**を記録し、推移を見る（前回より下がったら原因の Issue）。
- ユーザの実機確認を ISO 9241-210 の「評価」として正式工程にする。見つかった事象は Issue → 修正 → 予算に 1 行、の循環。

### やらないこと

- A/B テスト・利用テレメトリ（1 人のローカルアプリでは意味がなく [ADR-0010](0010-security-model.md) にも合わない）。
- 美的評価の点数化（測れない。重大度 1 として記録し、積み上がったら棚卸し）。
- SUS 10 問の常用（1 人には重い）。HEART の Engagement／Adoption／Retention（Web サービス向け）。
- 原則の独自定義（規格・研究にあるものを使う）。

## Consequences

- (+) 「ボタンが多い」が主観ではなく、Hick の法則に基づく予算超過として CI で赤くなる。UX の議論が原則名で行える。
- (+) 機能追加の PR は「複雑さを誰が負うか」を宣言する。足し算を止めるのではなく、負担の置き場を決めさせる。
- (+) ADR-0031 と同じ運用（ratchet・リスト縮小＝改善の実測値）なので学習コストが無い。
- (−) GUI の PR に 1 手（UX 欄・予算の更新）増える。それが議論のトリガーになるのが狙いなので仕様。
- (−) 予算の初期値は「現在値」で、最適値ではない。研究が示すのは方向で、数値はプロジェクトの運用値である点を文書に明記した。
- (−) KLM・WCAG・i18n 検査は未実装。実装 Issue で段階的に足す（文書の合意が先）。
