# ADR-0040: 協働ホストの常時起動・単独サーバの再探索・クライアント承認

- Status: Accepted（2026-11-23・ユーザ合意。ネットワーク越しの制御は過剰として採らない）
- Date: 2026-11-23
- 関係: [ADR-0033](0033-mcp-single-control-plane.md) D2 の「起動時に 1 回だけ探す」を**部分的に supersede** する。
  [ADR-0009](0009-p2-collab-host.md)（協働ホスト）・[ADR-0010](0010-security-model.md)（セキュリティモデル）・
  [ADR-0038](0038-mcp-stateless-realign.md)（stateless 化）を**補う**（それらの決定は存続する）。

この ADR で使う言葉:

- **ホスト**: GUI が起動する Node のサイドカー（`dist/mcp/host.cjs`）。deck の真実を持つ唯一の管制（ADR-0033 D1）。
- **アダプタ**: AI アプリが起動する `slidecraft mcp`（stdio）。ホストが見つかれば転送（forward）し、無ければ自分で単独（solo）の管制を持つ。
- **`host.json`**: ホストが待ち受けの URL と共有トークンを書く 0600 のファイル。アダプタはこれを読んでホストを探す。
- **共有トークン**: 起動ごとに作る 256 bit の bearer token（ADR-0010）。今はこれを持つ者は誰でもホストのツールを呼べる。
- **stdio**: AI アプリがサーバを子プロセスとして起動し、その標準入出力で MCP をやり取りする方式。アダプタはこの方式で動く。
- **HTTP 直結**: stdio を使わず、ホストの URL と共有トークンを AI アプリに直接設定してつなぐ方式（Cursor などの汎用 MCP クライアント）。送れる資格情報は `Authorization: Bearer` のヘッダだけである。
- **HMAC**: 秘密の鍵とメッセージから作る検証用の値（鍵付きハッシュ）。鍵そのものを送らずに「鍵を持っている」ことを示せる。
- **belt**: ADR-0010 の言葉で、主たる境界（token）を補う多層防御の一層のこと。それだけに頼ってはいけない守り。
- **`mcp-session-id`**: MCP の HTTP 経路で、ホストが `initialize` のときに発行し、クライアントが以後のリクエストに付けるセッションの識別子（`src/mcp/host.ts:109`）。

## Context

2026-11-08、Windows 11 と Claude Desktop（MSIX 版）で `.mcpb` を入れて GUI の協働につないだところ、次の手順が要った（#688）。

1. SlideCraft の GUI を起動する。
2. 協働 パネルで「協働を開始」を押す。押すまではホストが動かず、`host.json` も書かれない。
3. Claude Desktop を**完全に終了して起動し直す**。拡張の無効→有効では足りなかった（Claude Desktop はこの拡張のサーバを 2 つ起動しており、起動し直されたのは 1 つだけだった）。

ユーザの感想は「再起動しないとつながらないのがすごく不安。ユーザが意識することなく使えないと困る」。

これは設計どおりの挙動である。

- ホストは「協働を開始」を押したときだけ起動する（`src-tauri/src/collab.rs` の `start_collab`）。
- アダプタがホストを探すのは起動時の 1 回だけ（`src/mcp/cli.ts:88`。ADR-0033 D2）。見つからなければ、プロセスが終わるまで単独のまま。

目標は「起動の順序と再起動を利用者が意識しなくてよいこと」。GUI と AI アプリのどちらを先に起動しても、どちらを後から起動し直しても、次のツール呼び出しから同じ deck を見られるようにする。

2026-11-23 のユーザ裁定（#688 のコメント）で、「GUI の起動と同時にホストを起動する」と「単独のアダプタが後からホストを見つけたら乗り換える」の両方を採ると決まった。ただし、ホストが常に待ち受けるので、**`host.json` を読めた任意のプロセスがつながれるだけでは足りず、アクセス制御が要る**とされた。

調べて分かった前提（2026-11-23 の main `e80d7a5`）:

- 協働中の編集ロックは `editLocked = collab.status === "connected"`（`src/App.tsx:261`）。ホストにつないだ瞬間から、構造の変更・原稿・テンプレなどが止まる（#689 の表）。
- GUI と AI の区別は、自己申告のヘッダ `x-slidecraft-role` だけで決まっている（`src/mcp/host.ts:107`）。共有トークンを持てば誰でも GUI として振る舞える。ADR-0038 D3 は `/gui` を GUI 用のトークンで守ると決めたが、まだ実装されていない。
- 単独モードで deck を閉じるツールはない。`close_document` は協働の口だけに出している（`src/mcp/tool-profiles.ts:85`）。
- アダプタの転送（`src/mcp/mcp-relay.ts`）は、AI アプリが送った `initialize` をそのままホストへ流している。途中で単独から転送に切り替えると、ホストは `initialize` を受け取っていないことになる。
- ホストは今、`initialize` の `clientInfo`（クライアントが名乗る名前とバージョン）を使っていない。

## Decision

### D1. 常時ホスト — GUI の起動と同時にホストも起動する

- GUI を起動すると、ホストも起動して `host.json` を書く。「協働を開始」を押す手順はなくす。
- 止めたい人は、協働 パネルの「停止」で止め、「再開」で戻せる。停止はその起動のあいだだけ効く。起動時に毎回止めておきたい人向けの設定を足すかは、実装の Issue で UX 予算（ADR-0039）と合わせて決める。
- 次の守りは変えない: 待ち受けは 127.0.0.1 だけ・共有トークンは起動ごとに作る・`host.json` は 0600・Origin 許可リスト・終了時に `host.json` を消す（ADR-0009／0010）。
- **「ホストが動いている」と「協働中（編集ロック）」を分ける。** GUI の deck をホストに載せて編集ロックをかけるのは、**許可済みの AI クライアントから最初のツール呼び出しが来たとき**からにする。それまでの GUI は、ホストが無いときと同じように編集できる。ロックの範囲そのものの見直しは #689 で扱う。
- **deck を載せ終えるまで呼び出しを通さない。** 今は「協働を開始」のときに GUI がテンプレと deck をホストへ載せている（seed。`src/components/useCollab.ts:149-188`）。常時ホストでは、許可済みの AI の最初の呼び出しが、この seed より先に届くことがある。そのときホストは、seed が終わるまで呼び出しを短い時間だけ待たせる。間に合わなければ処理せずに `{ ok:false, code:"host-not-ready" }` を返し、少し待ってから呼び直すよう AI に伝える（never-silent）。空のホストを見せて、AI が「GUI に deck が無い」と誤解する経路は作らない。seed が失敗して終わった場合は、呼び出しを通したうえで、GUI の deck を載せられなかったことを `note` に書く（黙って空のまま進めない）。コードの綴りは既存の `GuardCode` に合わせて kebab-case にする。
  - 理由: `editLocked` が今のままだと、常時ホストにした瞬間に GUI の編集が起動直後から常に止まる。AI を使わない人にとって明らかな後退になる。
- ホストの起動はアプリの起動を止めない（今の `start_collab` は READY を受けるまで処理を止める。ADR-0009 の既知の課題）。起動に失敗しても（例: macOS の署名なし node が止められる）、モーダルは出さない。協働 パネルの状態行で知らせる（never-silent。黙って失敗しないという、このプロジェクトの原則）。

### D2. 再探索 — 単独のアダプタは呼び出しのたびにホストを探す

ADR-0033 D2 の「起動時に 1 回だけ判断する」を次の状態遷移に改める。管制は常に 1 つ、という ADR-0033 の不変条件は変えない。

| 今の状態 | ツール呼び出しが来たとき | 次の状態 |
|---|---|---|
| 単独・deck なし | `host.json` を読み、生きたホストがあれば転送に切り替えてからその呼び出しを転送する | 転送 |
| 単独・deck あり | **切り替えない。** 単独で処理し、返り値の `note` に「GUI の協働ホストが見つかりました。つなぐには、今の deck を保存してから `close_document` で閉じてください」と書く | 単独のまま |
| 転送 | そのまま転送する。ホストが応答しなくなっていたら、`host.json` を読み直す。新しいホストがあればそちらへつなぎ直し、無ければ単独・deck なしに戻り、`note` で知らせる | 転送 または 単独 |

- **確認の手間**: 単独のあいだは、呼び出しのたびに `host.json` を 1 回読む。生存確認の ping は、`host.json` の中身（URL・`startedAt`）が前回と変わったときだけ送る。中身の変わらない古い `host.json` に、毎回 1.5 秒の待ちを払わないためである。
- **単独の deck は黙って捨てない**（never-silent）。deck を持ったまま乗り換えないことで、捨てる経路そのものを作らない。
- **単独でも deck を閉じられるようにする**: 今の単独モードには閉じるツールがない。`close_document` を単独の口にも出す。未保存なら `force` が要るという今の規則がそのまま使えるので、新しいツールは作らない（ADR-0037 の「頻繁に呼ぶツールの面は最小に保つ」）。
- **切り替え時の手順**: 単独で受けた `initialize` の `clientInfo` をアダプタが覚えておき、乗り換えのときにアダプタ自身がホストとの手順（D3 の承認を含む）を行う。AI アプリには、ツールの一覧が変わったことを `notifications/tools/list_changed` で知らせる（単独と協働の口では一覧が少し違う。`tool-profiles.ts`）。この通知に応えないクライアントもあり得るので、一覧の違いで困らないかを結合テストで確かめる。
- **逆向き**（GUI が後から起動した・起動し直した）も同じ表で足りる。単独・deck なしなら次の呼び出しで転送になる。転送中にホストが落ちて戻ってきた場合は、「転送」の行でつなぎ直す。
- ADR-0038 の stateless 化（`initialize` の廃止）の後も、アダプタが AI アプリの名乗る名前を受け取って覚えるという形は変わらない。新しい版でその名前がどこに載るかは、実装時に仕様で確かめる。載っていなければ「不明なクライアント」として承認を求める（D3 の鍵には client ID が入るので、承認自体は成り立つ）。

### D3. クライアントの承認 — 初めて見るクライアントは GUI で許可を求める

共有トークンを持つことの意味を「ホストへ参加を申し込める」までに下げる。ツールを呼べるのは、利用者が GUI で許可したクライアントだけにする。

1. **鍵**: 「クライアントが名乗る名前（`clientInfo` の name・version）」と「アダプタが作る client ID」の組。
   - client ID はアダプタが初回に作り、資格情報ファイルに保存する。置き場は `host.json` と同じフォルダで、権限は 0600。AI アプリの名前ごとに 1 つ持つ。
   - 保存しないと、AI アプリを起動し直すたびに別の組になり、毎回許可を求めることになる。「初回だけ」を成り立たせるために必要な、`--no-fs` の新しい狭い例外である（ADR-0033 で認めた `host.json` の読み取りと同じ扱い）。
   - Claude Desktop のように同じアプリがサーバを 2 つ起動しても、同じファイルを共有するので許可は 1 回で済む。ファイルを最初に作るときは、同時に作られても 1 つに決まるようにする（排他的な作成）。
2. **承認ダイアログ**: 初めて見る組がつながってきたら、GUI に「〈Claude Desktop〉が SlideCraft への接続を求めています［許可］［拒否］」を出す。
   - **既定は拒否**: ダイアログを閉じた・無視した場合は拒否として扱う。拒否はそのホストの起動のあいだ覚えておき、同じ組には繰り返し尋ねない。
   - 承認を待っている件数は通知枠（`NoticeSlot`・#613）に出す。
   - 同じ組からの同時の申し込みは、ダイアログ 1 つにまとめる。
   - ダイアログには名前に加えて、client ID の短い指紋（先頭 8 文字）を出す。同じ名前を名乗る別の組を見分けるためである。HTTP 直結では client ID が無いので、`mcp-session-id` の先頭 8 文字を出す。
   - **連発への備え**: 別の client ID を次々に作って申し込むと、ダイアログが続けて出て、うっかり許可しやすくなる。そこで、ダイアログに［この起動中はすべて拒否］を置く。また、承認待ちは同時に 3 件までとし、それを超えた申し込みはダイアログを出さずに拒否する（`authorization-denied`。件数は `NoticeSlot` に出す）。
3. **承認を待つあいだ**: ツール呼び出しは短い時間だけ待ち、そのあいだに許可されれば続けて処理する。間に合わなければ `{ ok:false, code:"authorization-pending" }` を返し、AI には「SlideCraft の GUI で接続を許可してください」と伝える。コードの綴りは既存の `GuardCode` に合わせて kebab-case にする。拒否された場合は `authorization-denied` を返し、そのアダプタは単独のまま動く（GUI の deck には触れない）。
4. **クライアント別の秘密**: 許可すると、ホストはその組だけの秘密を発行する。
   - **ホスト側**: 許可した組と秘密は OS の keychain に保存する（ADR-0016 F3 と同じ `secret_store`）。keychain が無い環境（Secret Service の無い Linux など）では、F3 と同じく localStorage に置く。この場合は同じ OS ユーザから読めるが、GUI の webview が乗っ取られれば GUI 用のトークンで何でもできるので、新たに広がる危険はない。
   - **アダプタ側**: 資格情報ファイルに保存する（1 と同じファイル）。
   - **秘密を平文で送らない**（stdio のアダプタ経由の場合）: 秘密は通信に載せず、ホストが毎回出す nonce（使い捨ての乱数）に対する HMAC で示す。こうすると、古い `host.json` のポートを別のプロセスが使っていても、そのプロセスに長く使える秘密が漏れない。HTTP 直結では HMAC を計算できないので、この仕組みは使わない（7 を参照）。
   - **発行した秘密を渡す相手**: 申し込んだアダプタのプロセスだけが受け取れるようにする。申し込み時にアダプタがメモリだけに持つ使い捨ての値と結びつける。
5. **一覧と取り消し**: 協働 パネルに「接続を許可したクライアント」の一覧と［取り消し］を置く。#689 の 2 層化の上の層に、1 行＋折りたたみで収める。常に見えるボタンは増やさない（ADR-0039 の UX 予算）。
   - 取り消すと、その組の秘密を keychain とホストから消す。次の呼び出しは `authorization-revoked` になる。アダプタは自分の資格情報を消して、改めて許可を求める。
   - 共有トークンは作り直さないので、他のクライアントは落ちない。
6. **GUI は承認の対象外。ただし GUI であることをトークンで示す**: GUI は自分が起動したホストに対等なクライアントとしてつながる（ADR-0009）。そのため、`x-slidecraft-role` の自己申告ではなく、GUI 専用のトークンで GUI と認める（ADR-0038 D3 の `/gui` を前倒しで実装する）。GUI 専用のトークンは Rust がホストの起動時に受け取り、`host.json` には書かない。これが無いと、共有トークンを読んだプロセスが GUI を名乗って承認を素通りできる。
7. **承認の示し方は経路ごとに違う。**
   - **stdio のアダプタ経由**: 4 のとおり、クライアント別の秘密による nonce への HMAC で示す。秘密はアダプタの資格情報ファイルに残るので、AI アプリを起動し直しても許可は続く。
   - **HTTP 直結**: このクライアントは `Authorization: Bearer` に共有トークンを載せることしかできず、HMAC を計算できない。そこで、許可を**ホストが発行した `mcp-session-id` に結びつける**。`initialize` を受けたらその `clientInfo` で同じダイアログを出し、許可された `mcp-session-id` からのツール呼び出しだけを通す。入場判定（127.0.0.1・Origin 許可リスト・共有トークン）はこれまでどおり先に行う。
     - 許可の有効期間はその `mcp-session-id` が生きているあいだだけで、ホストの起動をまたがない。クライアントがつなぎ直すと（新しい `mcp-session-id`）、ダイアログがもう一度出る。
     - この経路で守られるのは「共有トークンを読んだだけの別のプロセスは、自分のセッションを利用者に許可されない限りツールを呼べない」ことまでである。許可済みの `mcp-session-id` を知ったプロセスは、共有トークンと合わせて、そのセッションとしてツールを呼べる（`mcp-session-id` は長く使える秘密ではないが、セッションのあいだは bearer の値として働く）。loopback の通信を盗み見るには通常は管理者権限が要るので、同じユーザの正規のツールがこの値を手にする経路は、そのクライアントのログや設定の漏れに限られる。
     - **期限付きの決定**: ADR-0038 は `Mcp-Session-Id` を廃止する（MCP 仕様 2026-07-28 版の stateless 化）。ホストを stateless にする段（#514 の段 4）では、この結びつけ先が無くなる。そのときの HTTP 直結の承認（例: GUI が組ごとの bearer を表示し、利用者がそれをクライアントに貼る）は、段 4 に着手する前に別の ADR で決める。それまで段 4 は、HTTP 直結の承認の置き換えを blocked-by に持つ。
8. **秘密を argv で渡さない**: 許可済みの一覧をホストへ渡すときは、GUI の口（GUI 専用トークンで守られた呼び出し）を使う。プロセスの引数には載せない（argv は他の OS ユーザからも見え得る）。

### 脅威モデル

| 脅威 | 今（ADR-0010） | この ADR の後 |
|---|---|---|
| 同じ OS ユーザで動く、利用者が意図していない正規のツール（MCP 設定を持つ別の AI アプリ・スクリプト） | `host.json` を読めれば、ツールを呼べる | 初めて見る組は承認ダイアログを通る。既定は拒否。許可した後も一覧に見えていて、取り消せる |
| 同じ OS ユーザ権限のマルウェア | 対象外（ADR-0010） | **対象外のまま。** 資格情報ファイルも keychain（Windows の資格情報マネージャーは同じユーザから読める）も読めるし、名前も偽れる。承認は、利用者の同意と見える化の仕組みであって、暗号的な本人確認ではない |
| 別の OS ユーザ | POSIX では 0600 で守る。Windows は ACL の明示的な制限が未実装で、ユーザごとのプロファイルの既定 ACL に頼っている | 0600 と既定 ACL は同じ。万一共有トークンを読まれても、承認を通らなければツールは呼べない。申し込みはダイアログとして利用者に見える |
| ブラウザからの CSRF・DNS rebinding | Origin 許可リスト（belt）＋ bearer token。ブラウザは token を付けられない | **守りの中心は変わらない**（token と Origin 許可リスト）。そのうえで、stdio 経由のツール呼び出しにはクライアント別の秘密による HMAC が、HTTP 直結のツール呼び出しには許可済みの `mcp-session-id` が要る。HTTP 直結の `mcp-session-id` は秘密としては弱いので、この経路の CSRF への守りは今と同じ強さであり、強くはならない |
| 共有トークンを読んだ別のプロセスが HTTP 直結を装う | `host.json` を読めれば、ツールを呼べる | 自分の `initialize` に対するダイアログを利用者が許可しない限り、ツールは呼べない。**守られないもの**: 許可済みの `mcp-session-id` を何らかの形で知ったプロセスは、そのセッションに相乗りできる（D3-7） |
| 古い `host.json`（GUI が異常終了して消えなかった・そのポートを別のプロセスが使っている） | 起動時に 1 回 ping する。応答した相手には共有トークンが渡る（死んだホストの token なので害は小さい） | 呼び出しのたびに確かめるので、ping は中身が変わったときだけにする。stdio 経由の長く使える秘密は HMAC で示し、平文では送らない。HTTP 直結は利用者が URL とトークンを手で設定する経路で、アダプタの探索を通らないので、この行の対象外 |
| 承認ダイアログの連発（承認疲れによる誤許可） | なし（承認が無い） | ［この起動中はすべて拒否］と、承認待ち 3 件の上限で抑える。ダイアログには client ID の指紋を出す（D3-2） |
| 自己申告の役割（`x-slidecraft-role: gui`）で GUI を名乗る | token が境界なので、名乗っても得はない（ADR-0009） | 承認を素通りする手段になるので、GUI 専用トークンで閉じる（D3-6） |

### 採らないもの

- 利用者にポートやトークンを入力させる方式。設定は stdio のコマンド 1 つのまま（ADR-0033 D2・ADR-0038）。
- ネットワーク越しの接続。待ち受けは 127.0.0.1 のままにする。
- 承認なしの自動接続。常時待ち受けと組み合わせると、`host.json` を読めた任意のプロセスが黙ってつながれてしまう。
- 単独の deck をホストへ引き渡すこと。引き渡しは deck の権威を途中で移すことであり、undo の履歴・dirty・テンプレの扱いを決める必要がある。閉じるまで乗り換えない方式で目標は満たせるので、今回は採らない。要望が出たら別の ADR で扱う。
- 常駐の daemon。ADR-0033 で検討して不採用にしたとおり。GUI がホストを持つ形を保つ。

## Consequences

- **UX（＋）**: 「協働を開始」を押す手順と、AI アプリの完全な再起動が要らなくなる。GUI と AI アプリのどちらを先に起動しても、次の呼び出しでつながる。
- **UX（−）**: 新しいクライアントが初めてつながるときに 1 回だけダイアログが出る。取り消した場合と、HTTP 直結の場合（つなぎ直すたび）にも出る。許可済みの AI の最初の呼び出しが seed より早いと、`host-not-ready` が返り、呼び直しが要る。単独で deck を持っているときは自動では乗り換えず、AI に閉じるよう伝える手順が残る。
- **UX（−）**: 協働の編集ロックがかかるきっかけが「開始を押したとき」から「許可済みの AI から最初の呼び出しが来たとき」に変わる。そのため、AI が動き出すと GUI の一部が止まる。何が止まるかを 1 か所で告げることは、#689 で一緒に解く。
- **セキュリティ（−）**: GUI を起動しているあいだは、常に loopback で待ち受ける。
- **セキュリティ（＋）**: 一方で、ツールを呼ぶには承認が要るようになる。今の「`host.json` を読めれば呼べる」より、同じユーザの意図しないツールに対しては強くなる。同じユーザのマルウェアに対しては変わらない（対象外のまま）。
- **複雑さ（−）**: keychain・承認ダイアログ・許可の一覧・資格情報ファイル・HMAC による確認・HTTP 直結の `mcp-session-id` への結びつけ・GUI 専用トークン・seed 完了までの待ち・アダプタの状態遷移が増える。
  - UX 予算の制約: 常に見えるボタンを増やさない。一覧は #689 の上の層に 1 行＋折りたたみで置く。承認待ちは `NoticeSlot` を使う。
  - `--no-fs` の例外は「`host.json` を読む」と「自分の資格情報ファイルを読み書きする」の 2 つになる。deck の中身には触れないという性質は変わらない。
- **資源（−）**: GUI を起動するたびに Node のサイドカーが 1 つ動く（メモリと起動時間）。アプリの起動を待たせないことを受け入れ条件にする。
- **テスト**: 結合テストで、ホストの起動と停止・承認（許可／拒否／取り消し）・単独から転送への乗り換え・ホストを起動し直したときのつなぎ直しを、テストの中で行う。#688 の受け入れ基準 2 つ（「AI アプリを先に起動し、後から GUI を起動しても、AI アプリを起動し直さずに次の `list_templates` で GUI のテンプレが返る」「GUI を起動し直しても、AI アプリを起動し直さずにつながり直る」）をここで固定する。
- **他の ADR との関係**:
  - ADR-0033 D2 の「起動時に 1 回だけ判断する」と `cli.ts` 冒頭の「再接続はしない（D2 の範囲外）」を、この ADR の D2 が置き換える。単一の管制・設定は stdio のコマンド 1 つ・転送は管制を持たない、は存続する。
  - ADR-0010 の「token が唯一の境界」に、承認とクライアント別の秘密を足す。loopback・Origin の belt・timing-safe な比較・do-NOT-undo のガードレールは存続する。
  - ADR-0009 の「協働を開始で起動する」流れを、GUI の起動時に起動する形に改める。サイドカーが真実を持つ形は存続する。
  - ADR-0038 D3 の GUI 専用トークンは、この ADR の前提として先に実装する（#730）。
  - ADR-0038 の stateless 化（`Mcp-Session-Id` の廃止）は、D3-7 の HTTP 直結の承認の結びつけ先を無くす。段 4 の前に置き換えを決める。

- **実装メモ（#727・2026-11-23）**: 入場判定（ADR-0010 の `checkRequest`／`admitRequest`）は今、(1) Host が loopback、(2) Origin 許可リスト、(3) 共有トークンか GUI 専用トークン、(4) GUI 専用トークン無しで `x-slidecraft-role` を名乗る要求は 403、の順で、GUI であることは GUI 専用トークンだけで決まる（#730）。ホストの READY 行は `{url, token, guiToken}` の 3 つを運ぶ（`guiToken` は `host.json` に書かない）。入場の後、AI のツール呼び出しはすべて承認の関門（`HostContext.admitCall`・`tool-profiles.ts` の登録ゲートで 1 か所）を通る。承認待ちは最大 30 秒、seed 待ちは最大 10 秒待ってから `authorization-pending`／`host-not-ready` を返す。待ち受けは 127.0.0.1 に固定し、他のアドレスを求める指定は拒否する（`src/mcp/host-options.ts`）。
- **実装メモ（#733 レビュー・2026-11-23）— D3 との差と補足**:
  - **HTTP 直結の拒否は「起動中は覚える」にならない（D3-2 との差）**: 承認の帳簿の鍵（組）は HTTP 直結では `mcp-session-id` を含む（D3-7 で許可をセッションに結びつけたため）。そのため［拒否］を覚えるのもそのセッションのあいだだけで、クライアントがつなぎ直すと（新しい `mcp-session-id`）ダイアログがもう一度出る。#728 で stdio アダプタが client ID を送るようになれば、組は `clientInfo`＋client ID になり、D3-2 のとおり起動中は覚える。それまでの連発は、承認待ち 3 件の上限と［この起動中はすべて拒否］で抑える。
  - **client ID が無い今は、Claude Desktop で許可のダイアログが 2 回出る（D3-1 との差）**: Claude Desktop は MCP サーバを 2 本起動し、今のアダプタは client ID を送らないので、ホストからは別々の HTTP 直結のセッションに見える。#728 で解消する。
  - **許可済みの組で証明に失敗した申し込みは、ダイアログを出さずに拒否する（D3-4 の補足）**: すでに許可のある組（同じ `clientInfo`＋client ID）を名乗って、nonce への HMAC が一致しない（証明が無い・nonce が古い場合を含む）申し込みは、新しい承認待ちにせず `authorization-denied`（理由 `proof-failed`）を返す。利用者には名前・版・指紋が同じで正規のアダプタと区別できず、許可すると秘密が作り直されて正規のアダプタの秘密が失効するためである。正規のアダプタが秘密を失った場合は、協働 パネルでその組の許可を取り消してから申し込み直す。この拒否は覚えない（正規のアダプタはその後も証明すれば通る）。
  - **keychain への保存失敗は告げる**: 許可を OS の資格情報ストアに保存できなかったときは、`NoticeSlot` の承認の帯（承認待ちが無いとき）に「次回の起動でもう一度許可を求める」と出す（閉じられる）。
